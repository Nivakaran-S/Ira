# Milestone 2: Core POS (online), design notes

**Date:** 2026-11-07. Builds on the platform spec (`2026-11-02-pos-platform-design.md`, §6, §8, §10).

## Decisions

| Topic | Decision |
|---|---|
| Money | Integers in minor units everywhere. Quantities in thousandths (`qtyMilli`), so weighed items (M6) need no schema change. |
| Pricing engine | `shared/src/pricing.ts`, pure. Inclusive prices are reversed with an exact rational factor (BigInt), and the rounding residue lands on the last rate so base + taxes = shelf price. Compound rates tax earlier rates. Line discounts apply first, then cart discounts are spread by largest remainder. |
| Server authority | The till sends `expectedTotal`; the API re-prices with the same engine and rejects any difference (`TOTAL_MISMATCH`). Payments must add up exactly (`PAYMENT_MISMATCH`). |
| Cash rounding | Per-tenant unit. Applies only when every payment is cash; stored as `Sale.rounding`, `due = total + rounding`. Refunds paid in cash round the same way. |
| Idempotency | Client-generated UUIDv7 sale and refund ids. A retry returns the stored row, and a race on the primary key falls back to the winner. |
| Receipt numbers | `{registerCode}-{000001}` from `Register.receiptSeq`; refunds use an `R` prefix on the same counter. M3 makes the till allocate locally. |
| Shifts | One open shift per register (partial unique index). Expected cash is computed from the ledgers (float + cash sales − cash refunds + pay-ins − pay-outs), never stored until close. |
| Step-up | `StepUpGate` consumes single-use tokens bound to the tenant, device and cashier; a request may carry several (comma-separated). Rules: price override and void always; no-sale drawer always; discounts if the cashier lacks `discount.apply` or exceeds `stepUp.discountAboveBp`; refunds if they lack `sale.refund` or exceed `stepUp.refundAbove`; pay-in/out and close if they lack `drawer.open` / `shift.close`. Approvals are stored on the sale and in the audit log. |
| Owner role | The system Owner role resolves to every permission at check time, so permissions added in later milestones reach existing owners. |
| Refund amounts | Per line, the share for (already refunded + this) minus the share already refunded, so partial refunds sum exactly to the line. An optimistic lock on `refundedQtyMilli` stops two concurrent refunds of the same line. |
| Stock | `StockLevel` (denormalised) + append-only `StockMovement`. Sales may drive stock negative; the back office flags it. |
| Append-only | `StockMovement`, `CashMovement`, `Payment`, `RefundLine`: the app role has no UPDATE/DELETE. |
| Receipts | The API builds a structured `ReceiptDoc`; the hardware bridge renders ESC/POS from it and never accepts raw bytes. The browser print dialog is the fallback. |
| Hardware bridge | `hardware-bridge/`, Node, `127.0.0.1:47800`. Paired once to a device key: the pairing request is signed by that key and needs a 6-digit code shown on the bridge console (5 wrong guesses burn it). Every later call carries the same signature headers as the API. CORS answers Chrome's Private Network Access preflight. |

## Out of this milestone

Email receipts (BullMQ) are deferred, and so is customer-facing display. Price lists (per store or customer group) are deferred to Milestone 7.
